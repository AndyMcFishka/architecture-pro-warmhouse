### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах [подтверждено условием, в предоставленном коде не реализовано]
- Всё управление идёт от сервера к модулям отопления [протокол доставки команд не описан]

**Телеметрия:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс [наличие веб-интерфейса подтверждено только условием]
- Сервер получает температуру через запросы к датчикам [в предоставленном коде — через внешний temperature-api]
- Система поддерживает просмотр списка сенсоров, информации по сенсору и температуры по локации
- Система поддерживает обновление значения и статуса сенсора

**Подключение и администрирование:**

- Подключение системы отопления требует выезда специалиста, пользователь не может самостоятельно подключить устройство [подтверждено условием]
- Датчики при включении регистрируются в системе [подтверждено схемой, механизм регистрации в коде не представлен]
- API позволяет добавлять/редактировать/удалять записи сенсоров [роль специалиста и принадлежность сенсоров пользователям в коде не реализованы]

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go 1.22
- Веб-фреймворк: Gin
- База данных: PostgreSQL, доступ через pgx и пул соединений pgxpool
- API: HTTP, данные передаются в JSON
- Архитектура: Монолитная, обработка запросов и работа с данными находятся в одном приложении. Код разделён на пакеты handlers, models, db и services. Отдельный слой бизнес-логики практически отсутствует
- Внешние зависимости: PostgreSQL и temperature-api. Реализация temperature-api в текущей заготовке отсутствует
- Взаимодействие: Синхронное. Сервер инициирует управление устройствами и получение температуры, устройства инициируют регистрацию. При получении списка температурные сенсоры опрашиваются последовательно [клиентские HTTP-запросы могут обрабатываться конкурентно]
- Развёртывание: Docker и Docker Compose [настройки PostgreSQL и temperature-api не завершены]. По условию обновление требует остановки приложения. В коде предусмотрено корректное завершение сервера

### 3. Определение доменов и границы контекстов

- **Регистрация и учёт устройств** — добавление, изменение и удаление записей об устройствах. Не отвечает за показания и команды оборудованию.
- **Телеметрия** — получение и просмотр текущей температуры и времени измерения. Не регистрирует устройства и не управляет отоплением.
- **Управление отоплением** — включение и выключение отопления по запросу пользователя. Не ведёт учёт устройств и показаний. Предусмотрено условием, но доставка команд в коде не реализована.

### **4. Проблемы монолитного решения**

- **Хранение данных** — описание сенсора и его последнее показание хранятся в одной таблице. Нет истории измерений, учёта домов и пользователей, привязки устройств к владельцам.
- **Актуальность показаний** — температура из внешнего API не сохраняется в БД. При сбое API запрос сенсора или списка возвращает сохранённые, возможно устаревшие данные, а запрос по локации — ошибку.
- **Производительность и масштабирование** — сенсоры опрашиваются последовательно, поэтому с ростом их числа ответ замедляется. Таймаут одного запроса — 10 секунд. Компоненты монолита нельзя масштабировать отдельно.
- **Безопасность** — нет аутентификации и проверки прав: API не проверяет, кому принадлежит устройство и кто может с ним работать.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```
